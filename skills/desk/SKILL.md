# agent-desk 기록 규칙

에이전트가 태스크 단위의 현황, 결정, 로그를 세션을 넘어 이어가기 위한 개인용 기록 공간(데스크)이다.

태스크 생성·종료와 프로젝트 등록은 이 스킬의 base directory에 있는 절차 파일을 읽고 따른다: `new.md`(태스크 생성), `close.md`(종료·아카이브), `init.md`(프로젝트 등록).

## 용어

사용자와 에이전트가 같은 이름으로 부른다. 짧게 부르고, 문맥으로 해석하고, 모호하면 한 줄로 되묻는다. 사용자에게 말하거나 기록할 때도 이 이름을 쓴다.

| 이름 | 가리키는 것 |
|---|---|
| 데스크 | agent-desk가 관리하는 기록 전체(태스크 기록 + 지식). "데스크에 남겨줘", "데스크 점검해줘" |
| 프로젝트 | 등록한 저장소 |
| 태스크 기록 | 태스크 하나의 현황·결정·로그 |
| 현황 | state.md. "상태"는 태스크 상태에만 쓴다 |
| 태스크 상태 | 예정 `todo`(만들어 두고 착수 전), 진행 중 `in_progress`, 보류 `on_hold`(착수했다가 멈춤·기다림), 완료 `done`, 취소 `cancelled`(이루지 않고 종료). 앞의 셋이 **열린 태스크**, 뒤의 둘이 **종료된 태스크**(아카이브) |
| 결정 | decisions.md의 항목(D번호). 지식의 decision 항목도 "결정"이라 부르며 문맥과 번호(D/K)로 구분한다. 둘이 함께 나오는 맥락에서는 "태스크 결정"과 "설계 결정"으로 나눠 말한다 |
| 로그 | log.md |
| 지식 | knowledge 항목(K·G번호). 일반적인 뜻의 지식과 구분이 필요하면 "knowledge"라고 쓴다. 종류는 설계 결정(decision)·함정(pitfall)·발견(finding)·방법(howto), 상태는 유효·재확인 필요(stale)·대체됨·폐기(retired)·삭제 |
| 상위·하위·연관 태스크 | parent, 그 아래 태스크, related |
| 포커스 | 이 세션이 작업하는 태스크. 사용자의 요청으로 정한다(`adesk focus`). 세션마다 따로 있고 다른 세션·PC와 공유하지 않는다. 기록은 포커스 태스크에 한다 |
| 아카이브 | 종료된 태스크를 옮겨 두는 곳 |
| 휴지통으로 옮기기 / 영구 삭제 | 태스크 삭제는 휴지통(`trash/`)으로 옮기기이고 되살릴 수 있다. 영구 삭제는 휴지통의 태스크를 지운다. 지식의 "삭제"(내용을 지우고 ID만 남김)와는 다르다 |
| 데스크 점검 | `adesk doctor` |

## CLI

`adesk`로 실행한다. Claude Code가 플러그인 `bin/`을 셸 도구의 PATH에 넣고, Bash는 `bin/adesk`, PowerShell·cmd는 `bin/adesk.cmd`를 쓴다. `adesk`를 찾지 못하면 `adesk` 대신 이 스킬의 base directory 기준 `../../bin/desk.py`를 `python`으로 실행한다.

```
# 조회
adesk where                             # 프로젝트, 이 세션의 포커스(focus), 이 브랜치의 태스크(branch_task)
adesk list [--all]                      # 태스크 목록 (--all: 아카이브 포함)
adesk list --deleted                    # 휴지통의 태스크 목록

# 포커스
adesk focus <id>                        # 이 세션의 포커스를 정하고 기록을 텍스트로 출력 (todo면 진행 중으로)
adesk focus --clear                     # 이 세션의 포커스 해제

# 생성
adesk new --title "제목"                  # 현재 브랜치로 태스크 생성 (포커스가 됨, --no-focus)
adesk new --title "제목" --no-branch --slug survey-x   # 브랜치 없는 태스크
adesk new --title "제목" --no-branch --slug x --todo   # 예정 태스크 (포커스 안 됨)
adesk new --title "제목" --parent <id> [--related a,b]   # 상위·연관 태스크 지정

# 기록 쓰기
adesk put <데스크 파일> --file <파일|-> [--verified]   # 본문 교체 (frontmatter는 현재 값 유지)
adesk append <데스크 파일> --file <파일|->   # 끝에 덧붙이기

# 속성·관계 (frontmatter)
adesk set <id> [--title "제목"] [--design-doc URL] [--add-link URL] [--remove-link URL]
adesk link <id> [--branch B]            # 태스크에 브랜치 추가
adesk unlink <id> [--branch B]          # 브랜치 연결 해제(버린 브랜치 정리)
adesk relate <id> [--parent P | --no-parent] [--add a,b] [--remove a,b]

# 상태·종료·삭제
adesk status <id> todo|in_progress|on_hold
adesk close <id> done|cancelled [--note "..."]
adesk reopen <id>
adesk delete <id>                       # 휴지통으로 옮기기 (열린·종료된 태스크 모두)
adesk restore <id>                      # 휴지통에서 되살리기 (상태에 따라 tasks/ 또는 archive/로)
adesk delete <id> --purge               # 휴지통의 태스크를 영구 삭제

# 지식·점검·관리
adesk kn search|show|list|add|set|supersede|retire|delete|verify|stale ...   # knowledge (agent-desk:kn 스킬)
adesk doctor [--apply]                  # 낡은 knowledge·충돌 사본·방치된 태스크 점검 (agent-desk:kn 스킬)
adesk index                             # 태스크·knowledge index.md 재생성
adesk migrate [--dry-run]               # 데이터 폴더를 현재 스키마로 변환
```
`--project KEY`와 `--cwd DIR`은 하위 명령 **앞에** 둔다. 출력은 JSON이다(`focus`는 태스크 기록 텍스트, `kn list`는 항목당 한 줄 텍스트).

ID 생성, 브랜치 중복 검사, 상태 전환, 아카이브·휴지통 이동은 반드시 CLI로 한다. 폴더를 직접 만들거나 옮기거나 지우지 않는다.

**frontmatter는 CLI가 쓰고, 글(본문, log.md, decisions.md)은 에이전트가 쓴다.** frontmatter 값은 전용 명령으로 바꾼다: 태스크의 제목·설계 문서·링크는 `set`, 상태는 `status`·`close`, 브랜치는 `link`·`unlink`, 상위·연관 태스크는 `relate`, knowledge는 `kn set`(제목·종류·location·paths·tags·sources)과 `kn verify` 등. 제목 변경은 오타 수정용이고, 일의 범위나 내용의 의미가 바뀌면 새 태스크·새 항목으로 만든다. `updated`는 CLI가 태스크 파일을 쓸 때 자동으로 바뀐다.

## 저장 구조

```
<root>/projects/<KEY>/project.toml        # 프로젝트 설정 (id_template, shared_branches)
<root>/projects/<KEY>/index.md            # 자동 생성, 직접 수정 금지
<root>/projects/<KEY>/tasks/<id>/state.md       # 현황: 덮어씀
<root>/projects/<KEY>/tasks/<id>/decisions.md   # 결정: 항목 추가
<root>/projects/<KEY>/tasks/<id>/log.md         # 로그: 덧붙이기만
<root>/projects/<KEY>/archive/<id>/...    # 종료된 태스크
<root>/projects/<KEY>/trash/<id>/...      # 휴지통 (목록·주입·브랜치 매칭에서 빠짐)
<root>/projects/<KEY>/knowledge/K0001-*.md      # 프로젝트 knowledge
<root>/knowledge/G0001-*.md               # 전역 knowledge
```

## 태스크 생성 기준

- 사용자가 지시하면 만든다.
- 사용자가 **목표가 있는 새 일**(기능 구현, 버그 수정, 리팩터링처럼 세션을 넘겨 이어질 일)을 시작하려 하면, 착수 전에 태스크로 기록할지 한 줄로 묻는다. 브랜치가 필요하면 같은 질문에서 함께 제안한다. 이 세션에서 새 브랜치를 만들었을 때도 같다.
- 묻지 않는 것: 잠깐의 질문, 조사, 일회성 수정, 이미 있는 태스크 범위의 일. 이런 것마다 태스크를 만들면 기록이 소음이 된다. 사용자가 거절한 일은 그 세션에서 다시 묻지 않는다.
- 만들 때 사용자가 정한 목표와 범위를 현황에 적는다.
- 지금 착수하지 않을 일을 잊지 않게 남겨 달라고 하면 예정 태스크(`--todo`)로 만든다. 예정 태스크에 포커스하면 진행 중이 된다.
- 만들기로 하면 `new.md` 절차를 따른다. 프로젝트가 등록되지 않았으면 `init.md` 절차를 먼저 안내한다.

## 포커스 (이 세션의 태스크)

세션에서 무슨 일을 할지는 사용자가 정한다. SessionStart는 태스크 기록을 넣지 않고 후보만 알린다(이 브랜치에 연결된 태스크, 없으면 열린 태스크 전체). 에이전트는 사용자의 요청을 보고 `adesk focus <id>`로 포커스를 정하고, 출력된 기록(현황·결정 목록·상위 태스크)을 읽고 시작한다.

- **이 브랜치에 연결된 태스크가 기본값이다.** 첫 요청이 이 브랜치의 작업이면("이어서 하자", 코드 수정, 버그 조사) 묻지 않고 포커스한다. 요청이 다른 태스크를 가리키거나 관련이 애매하면 묻는다.
- 브랜치에 연결된 태스크가 없으면 기본값이 없다. 요청이 후보 중 하나를 분명히 가리키면 포커스하고, 아니면 묻는다.
- 태스크와 무관한 세션(가벼운 질문 등)이면 포커스하지 않는다. **포커스 전에는 기록하지 않는다.** 기록할 일이 생기면 어느 태스크에 남길지 묻는다.
- `new`로 만든 태스크는 이 세션의 포커스가 된다(`--todo`는 안 됨).
- 포커스는 이 세션에서만 유지된다. 압축·재개 뒤에는 SessionStart가 그 기록을 다시 주입하고, `/clear`는 새 세션이라 다시 고른다. 다른 세션·다른 PC와 공유되지 않는다.
- 다른 태스크로 넘어갈 때는 사용자에게 확인하고 `focus <id>`로 옮긴다. 포커스 태스크를 닫으면(`close`) 포커스는 없어진다. 상위 태스크로 이어 갈지 사용자에게 묻는다.
- 세션 중에 저장소나 브랜치가 바뀌면 "작업 위치가 바뀌었다" 블록으로 새 위치의 후보가 표시된다(worktree 진입·이탈은 즉시, 터미널에서 바꾼 브랜치는 다음 프롬프트에서). 사용자의 일이 그 브랜치의 태스크로 바뀌었으면 `focus`로 옮긴다. 직접 Bash로 브랜치를 바꿨다면 주입을 기다리지 말고 `where`로 확인한다.
- "이 세션의 포커스가 바뀌었다" 안내가 나왔는데 직접 바꾼 것이 아니면, 서브에이전트가 바꾼 것이다. 사용자에게 알리고 `focus`로 바로잡는다.

## 상위 태스크와 연관 태스크

- **상위 태스크(`parent`)**: 여러 브랜치로 나뉘어 진행되는 큰 흐름(예: 여러 모듈의 독립화)을 묶는다. 상위 태스크는 보통 브랜치 없는 태스크(`--no-branch`)으로 만들고, 각 브랜치 태스크를 `--parent`로 그 아래에 둔다. 계층은 한 단계만 허용된다.
  - 하위 태스크 세션에는 상위 태스크의 state.md 전문과 결정 제목이 함께 주입된다. 이 세션의 할 일은 하위 태스크 state.md를 따른다. **상위 태스크의 유효한 결정을 따른다.** 어긋나는 결정이 필요하면 사용자에게 확인한다.
  - 흐름 전체에 걸친 결정은 상위 태스크의 decisions.md에, 이 브랜치에만 해당하는 결정은 하위 태스크의 decisions.md에 기록한다.
  - 상위 태스크의 state.md는 흐름 전체의 목표와 하위 태스크에서 나온 결과를 짧게 유지한다. 하위 태스크 목록은 `parent`로 `list`에서 알 수 있으므로 state.md에 나열하지 않는다. 하위 태스크에서 단계가 끝나거나 하위 태스크가 종료되면 상위 태스크의 "현재 상태"에 결과를 한 줄 반영한다.
- **연관 태스크(`related`)**: 후속 태스크, 같은 영역의 이전 태스크 등 의미를 정하지 않은 참조 목록이다. 주입되지 않고 ID만 표시되므로, 필요할 때 `list --all`로 위치를 찾아 읽는다.

## 서브에이전트에 일을 맡길 때

- 서브에이전트는 메인 세션과 같은 세션 ID를 쓴다. 그래서 **서브에이전트는 이 세션의 포커스를 바꾸지 않는다**(`focus` 금지, 태스크를 만들면 `new --no-focus`). 메인 에이전트는 서브에이전트에 넘기는 지시에 태스크 ID와 이 절의 규칙을 넣는다.
- 포커스 태스크 범위 안의 일을 맡기면, 서브에이전트는 그 태스크 ID로 기록한다.
- 다른 태스크의 일을 맡기면, 서브에이전트는 지시받은 태스크 ID를 명시해 기록한다(`kn add --sources <id>` 등). 포커스에 기대지 않는다.
- worktree를 쓸지는 사용자의 지시를 따른다. worktree에서 브랜치를 만들어 태스크에 이어 둘 일이면 `link <id>`로 연결한다.
- 서브에이전트는 세션 시작 주입을 받지 않으므로 태스크와 상위 태스크의 state.md·decisions.md를 직접 읽는다. 서브에이전트의 Bash `cd`는 다음 호출로 이어지지 않으니 기대지 않는다.
- 각 에이전트는 자기 태스크 기록만 고친다. 상위 태스크 반영(현재 상태 한 줄, 흐름 전체의 결정)은 메인 에이전트가 결과를 모아 한다. 동시에 고치면 서로 덮어쓴다.
- main 병합·푸시는 메인 에이전트가 결과를 모은 뒤 한 번에 한다.

## 파일별 작성 규칙

데스크 파일은 Edit/Write 도구로 고치지 않는다(hook이 거부한다). rewind(Restore code)는 Edit/Write로 바꾼 것만 되돌리고 CLI로 바꾼 것은 남겨서, 섞어 쓰면 데스크가 어긋난다. 내용은 scratchpad(없으면 작업 디렉터리 밖 임시 폴더)에서 만들고 CLI로 반영한다. sed 등으로 직접 고치지 않는다(조용히 실패할 수 있다).
- 고치기(state.md, decisions.md의 기존 항목, knowledge 본문): 데스크 파일을 scratchpad에 `cp`로 복사하고, 사본을 Read·Edit한 뒤 `adesk put <데스크 파일> --file <사본>`. put은 frontmatter 전체를 현재 파일 값으로 유지하므로(사본에는 본문만 있어도 된다) 사본의 frontmatter를 고쳐도 반영되지 않는다. 사본과 달랐던 키는 출력의 `kept`로 알린다.
- 덧붙이기(log.md 항목, decisions.md의 새 결정): 덧붙일 부분만 scratchpad 파일에 Write하고 `adesk append <데스크 파일> --file <파일>`. 짧으면 `--file -`와 heredoc으로 표준 입력에 넘겨도 된다.
- 데스크 파일 경로는 절대 경로나 데이터 폴더 기준 상대 경로(`projects/<KEY>/tasks/<id>/state.md`)로 쓴다. 새 파일은 만들지 않는다(태스크와 knowledge 파일은 `new`·`kn add`가 만든다).

모든 파일은 UTF-8(BOM 없음), LF로 저장한다(put·append가 BOM과 CRLF를 정리한다).

CLI 인자로 넘기는 값은 CLI가 따옴표를 붙여 쓰니 그대로 넘긴다. 쉼표로 구분하는 목록(`--paths`, `--tags`, `--related`)의 항목에는 쉼표를 넣을 수 없다. 현재 파일의 frontmatter를 읽을 수 없을 때만 put이 사본의 frontmatter를 쓴다(고치는 경우). 이때는 맨 앞 열의 `key: 값`과 한 줄 목록(`[a, "b, c"]`)으로 쓰고, `#`나 `: `가 들어간 값은 따옴표로 감싼다.

### state.md (현황, 덮어씀)
- 세션 시작 시 이것만 읽어도 이어서 작업할 수 있게 쓴다. **60줄 이내**를 유지하고, 넘으면 지난 내용을 log.md로 옮긴다.
- 섹션: 목표 / 현재 상태 / 다음 할 일 / 미해결 질문 / 핵심 파일(`경로:줄 — 역할`) / 관련 지식(`- K0012 제목`).
- Claude Docs 설계 문서 URL은 `set <id> --design-doc <URL>`로, 이슈·PR 등 링크는 `set <id> --add-link <URL>`로 둔다(아래 "문서 위치 기준").
- 내용을 코드와 대조해 확인했다면 `put --verified`로 반영한다(`verified` 갱신).
- 커밋 해시는 적지 않는다(rebase로 바뀐다). 브랜치명과 커밋 메시지로 가리킨다.

### decisions.md (결정, 항목 추가)
- 사용자와 방향을 확정한 **즉시** 기록한다. 나중으로 미루지 않는다.
- 형식: `## Dn. 제목  (YYYY-MM-DD, 유효)` 아래에 결정 / 이유 / 기각한 대안 / 영향 범위. 세션 주입이 이 머리 줄로 결정 목록을 만든다. put·append가 형식이 어긋나거나 번호가 빠지거나 겹치면 출력의 `warnings`로 알리니 고친다.
- 결정이 바뀌면 기존 항목을 지우지 않는다. 상태를 `대체됨 → Dm`으로 바꾸고 새 항목을 추가한다.
- 기각한 대안과 그 이유를 꼭 남긴다. 같은 논의를 반복하지 않게 하는 핵심 정보다.

### log.md (히스토리, 덧붙이기만)
- `## YYYY-MM-DD HH:MM` 아래에 짧은 bullet로 적는다. 기존 항목은 수정하지 않는다. 시각은 짐작하지 말고 `date`로 확인해서 쓴다.
- 무엇을 했는지보다 **무엇을 알아냈는지**(원인, 확인한 사실, 막힌 지점)를 중심으로 쓴다.

## 갱신 시점

- 결정을 확정했을 때: decisions.md에 즉시 기록. 그 결정이 knowledge 기준(`agent-desk:kn` "무엇을 어디에 두는가")에 맞으면 knowledge 기록도 제안한다.
- 함정이나 원인을 밝혀냈을 때: log.md에 기록하고, knowledge 기준에 맞으면 기록을 제안한다.
- 의미 있는 단계가 끝났을 때(원인 규명, 구현 완료, 방향 전환): state.md 갱신 + log.md 항목 추가.
- 사용자가 태스크를 마무리하거나 세션을 정리하려 할 때: state.md의 "다음 할 일"이 최신인지 확인.
- 컨텍스트 압축 직후(세션 컨텍스트에 압축 안내가 있을 때): 빠진 내용을 기록.
- 마일스톤(설계 확정, 구현 단계 완료)에서 설계 문서(`design_doc`)가 있으면 decisions.md를 바탕으로 갱신한다.
- 구현이 끝났을 때(PR 전): 아래 "저장소 문서"에 따라 반영이 필요한지 확인해 제안한다.
- 갱신은 짧게 하고, 사용자에게는 "agent-desk 갱신" 정도로 한 줄만 알린다.

## 문서 위치 기준

| 내용 | 위치 | 쓰는 시점 |
|---|---|---|
| 태스크 단위 설계: 배경, 목표, 대안, 결정, 진행 | Claude Docs 설계 문서 (`state.md`의 `design_doc`) | 설계 단계부터 태스크와 함께 |
| 시스템의 현재 구조·기능·데이터 포맷·도메인 | 저장소 문서 (프로젝트 지침이 가리키는 위치) | 프로젝트 지침을 따른다 |
| 코드에 남기기 어려운 원자적 사실: 함정, 원인, 방법, 설계 결정 | knowledge 항목 (`agent-desk:kn` 기준) | 발견 즉시 |
| 사용자와 일하는 방식 | 에이전트 메모리 | 교정을 받았을 때 |
| 어떤 작업에서든 미리 알아야 하는 환경 규칙 | 사용자 전역 지침 (`~/.claude/CLAUDE.md`) | 발견 즉시, 사용자가 동의하면 |

### Claude Docs 설계 문서
- 아래 중 하나 이상에 해당하면 만들기를 제안하고, 만들기 전에 사용자에게 한 줄로 확인한다.
  - 여러 세션에 걸칠 태스크
  - 대안을 비교해 고른 설계 결정이 있음
  - 여러 모듈이나 계층(코드, 데이터, 에셋, 서버/클라)에 걸친 변경
  - 리뷰하거나 공유할 예정
- 문서는 docs 스킬(예: `anthropic-skills:docs`)의 절차로 만들고, URL을 `state.md`의 `design_doc`에 기록한다.
- `decisions.md`가 원본이고 설계 문서는 사람이 읽는 정리본이다. 설계 문서의 각 결정에 `D3`처럼 원본 번호를 표시해 추적할 수 있게 한다.

### 저장소 문서
- 구현이 끝났을 때(PR 전)와 태스크를 종료할 때, 태스크가 바꾼 시스템의 동작이 저장소 문서와 어긋나지 않는지 decisions.md·log.md를 근거로 확인하고, 반영이 필요하면 제안한다.
- 무엇을 어떻게 문서화할지는 프로젝트 지침을 따른다.

## 읽을 때의 태도

- 기록은 **확인할 출발점**이지 사실이 아니다. `verified` 날짜가 오래되었거나 코드와 어긋나면 코드를 우선하고 기록을 고친다.
- log.md는 필요할 때만 검색해서 읽는다. 통째로 읽지 않는다.
- 기존 설계를 바꾸거나 되돌리자고 제안하기 전에는 종료된 태스크를 포함해 decisions.md에서 이전 결정과 기각한 대안을 확인한다.
- 세션 컨텍스트에 동기화 충돌 사본 경고가 있으면 사용자에게 알리고 병합 여부를 확인한다.

## 종료와 재개

종료는 `close.md` 절차를 따른다. 멈출 때는 `status <id> on_hold`, 다시 시작할 때는 `status <id> in_progress`를 쓴다.

- 하려다 그만둔 일은 `close <id> cancelled`로 기록을 남긴다. 잘못 만들었거나 중복인 태스크는 `delete <id>`로 휴지통에 옮긴다. 되살릴 때는 `restore <id>`.
- 영구 삭제(`delete <id> --purge`)는 사용자가 명시적으로 요청할 때만 한다. 출력의 `note`(동기화·백업의 버전 기록에는 남을 수 있음)를 사용자에게 전한다.
- 휴지통의 태스크는 목록·주입·브랜치 매칭에서 빠진다. 그 태스크를 가리키던 상위·연관 태스크는 그대로 두며 되살리면 다시 이어진다. 포커스 태스크를 옮기면 포커스는 없어지고, 같은 세션에서 되살리면 다시 포커스가 된다.
