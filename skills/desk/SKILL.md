# agent-desk 기록 규칙

에이전트가 태스크 단위의 현황, 결정, 로그를 세션을 넘어 이어가기 위한 개인용 기록 공간(데스크)이다.

## 용어

사용자와 에이전트가 같은 이름으로 부른다. 짧게 부르고, 문맥으로 해석하고, 모호하면 한 줄로 되묻는다. 사용자에게 말하거나 기록할 때도 이 이름을 쓴다.

| 이름 | 가리키는 것 |
|---|---|
| 데스크 | agent-desk가 관리하는 기록 전체(태스크 기록 + 지식). "데스크에 남겨줘", "데스크 점검해줘" |
| 프로젝트 | 등록한 저장소 |
| 태스크 기록 | 태스크 하나의 현황·결정·로그 |
| 현황 | state.md. "상태"는 태스크 상태에만 쓴다 |
| 태스크 상태 | 예정 `todo`(만들어 두고 착수 전), 진행 중 `in_progress`, 보류 `on_hold`(착수했다가 멈춤·기다림), 완료 `done`, 취소 `cancelled`(이루지 않고 종료). 앞의 셋이 **열린 태스크**, 뒤의 둘이 **종료된 태스크**(아카이브) |
| 결정 | decisions.md의 항목(D번호). 지식의 decision 항목도 "결정"이라 부르며 문맥과 번호(D/K)로 구분한다. 둘이 함께 나오는 맥락에서는 "태스크 결정"과 "설계 결정"으로 나눠 말한다 |
| 로그 | log.md |
| 지식 | knowledge 항목(K·G번호). 일반적인 뜻의 지식과 구분이 필요하면 "knowledge"라고 쓴다. 종류는 설계 결정(decision)·함정(pitfall)·발견(finding)·방법(howto), 상태는 유효·재확인 필요(stale)·대체됨·폐기(retired)·삭제 |
| 상위·하위·연관 태스크 | parent, 그 아래 태스크, related |
| 포커스 태스크 | 브랜치 없이 일할 때 세션이 다루는 태스크 |
| 아카이브 | 종료된 태스크를 옮겨 두는 곳 |
| 휴지통으로 옮기기 / 영구 삭제 | 태스크 삭제는 휴지통(`trash/`)으로 옮기기이고 되살릴 수 있다. 영구 삭제는 휴지통의 태스크를 지운다. 지식의 "삭제"(내용을 지우고 ID만 남김)와는 다르다 |
| 데스크 점검 | `adesk doctor` |

## CLI

Bash 도구에서 `adesk`로 실행한다(Claude Code가 플러그인 `bin/`을 Bash 도구의 PATH에 넣는다). PowerShell 등 다른 셸이거나 `adesk`를 찾지 못하면 `adesk` 대신 이 스킬의 base directory 기준 `../../bin/desk.py`를 `python`으로 실행한다.

```
adesk where                             # 현재 저장소·브랜치의 프로젝트와 태스크
adesk list [--all]                      # 태스크 목록 (--all: 아카이브 포함)
adesk new --title "제목"                  # 현재 브랜치로 태스크 생성
adesk new --title "제목" --no-branch --slug survey-x
adesk new --title "제목" --parent <id> [--related a,b]   # 상위·연관 태스크 지정
adesk link <id> [--branch B]            # 태스크에 브랜치 추가
adesk relate <id> [--parent P | --no-parent] [--add a,b] [--remove a,b]
adesk focus [<id> | --clear]            # 포커스 태스크 조회·지정·해제
adesk new --title "제목" --no-branch --slug x --todo   # 예정 태스크로 생성 (포커스 안 됨)
adesk status <id> todo|in_progress|on_hold
adesk close <id> done|cancelled [--note "..."]
adesk reopen <id>
adesk delete <id>                       # 휴지통으로 옮기기 (열린·종료된 태스크 모두)
adesk restore <id>                      # 휴지통에서 되살리기 (상태에 따라 tasks/ 또는 archive/로)
adesk delete <id> --purge               # 휴지통의 태스크를 영구 삭제
adesk list --deleted                    # 휴지통의 태스크 목록
adesk index                             # 태스크·knowledge index.md 재생성
adesk kn search|list|add|supersede|retire|delete|verify|stale ...   # knowledge (agent-desk:kn 스킬)
adesk doctor [--apply]                  # 낡은 knowledge·충돌 사본·방치된 태스크 점검 (agent-desk:kn 스킬)
adesk migrate [--dry-run]               # 데이터 폴더를 현재 스키마로 변환
```
`--project KEY`와 `--cwd DIR`은 하위 명령 **앞에** 둔다. 출력은 JSON이다.

ID 생성, 브랜치 중복 검사, 상태 전환, 아카이브·휴지통 이동은 반드시 CLI로 한다. 폴더를 직접 만들거나 옮기거나 지우지 않는다.

## 저장 구조

```
<root>/projects/<KEY>/project.toml        # 프로젝트 설정 (id_template, shared_branches)
<root>/projects/<KEY>/index.md            # 자동 생성, 직접 수정 금지
<root>/projects/<KEY>/tasks/<id>/state.md       # 현황: 덮어씀
<root>/projects/<KEY>/tasks/<id>/decisions.md   # 결정: 항목 추가
<root>/projects/<KEY>/tasks/<id>/log.md         # 로그: 덧붙이기만
<root>/projects/<KEY>/archive/<id>/...    # 종료된 태스크
<root>/projects/<KEY>/trash/<id>/...      # 휴지통 (목록·주입·브랜치 매칭에서 빠짐)
<root>/projects/<KEY>/knowledge/K0001-*.md      # 프로젝트 knowledge
<root>/knowledge/G0001-*.md               # 전역 knowledge
```

## 태스크 생성 기준

- 사용자가 지시했을 때, 또는 이 세션에서 **새 브랜치를 만들었을 때만** 만든다. 브랜치를 만든 경우에는 만들기 전에 사용자에게 한 줄로 확인한다.
- 그 외에는 만들지 않는다. 잠깐의 질문, 조사, 일회성 수정마다 태스크를 만들면 기록이 소음이 된다.
- 지금 착수하지 않을 일을 잊지 않게 남겨 달라고 하면 예정 태스크(`--todo`)로 만든다. 예정 태스크를 포커스로 지정하면 진행 중이 된다. 브랜치로 매칭된 예정 태스크에서 작업을 시작하면 `status <id> in_progress`로 바꾼다.
- 프로젝트가 등록되지 않았으면 `agent-desk:desk-init` 절차를 먼저 안내한다.

## 세션의 태스크와 포커스

세션이 다루는 태스크는 다음 순서로 정해지고, SessionStart가 그 태스크를 주입한다.
1. 현재 브랜치에 연결된 태스크
2. 없으면 프로젝트의 **포커스 태스크** (`· 포커스`로 표시)
3. 둘 다 없으면 태스크 없음. 프로젝트의 열린 태스크 목록 전체가 함께 표시된다.

태스크가 주입될 때는 다른 열린 태스크의 건수만 한 줄로 표시된다. 사용자가 다른 태스크를 물으면 `list`로 조회한다.

- `main`에서만 개발하는 프로젝트처럼 공용 브랜치에서 일할 때는 브랜치 없는 태스크와 포커스로 운영한다. 공용 브랜치에서 `new --no-branch`로 만든 태스크는 자동으로 포커스가 되고, 그 태스크를 `close`하면 포커스도 해제된다.
- 다른 브랜치 없는 태스크로 넘어갈 때는 사용자에게 확인하고 `focus <id>`로 바꾼다.
- 태스크가 연결되지 않은 기능 브랜치에서 포커스 태스크가 표시되면, 이 브랜치의 일과 관계없을 수 있다. 관계없으면 사용자에게 확인하고 새 태스크를 만들거나 `link`로 연결한다.
- 포커스 태스크가 현재 브랜치 태스크와 별개라는 안내가 나오면, 포커스가 낡았는지 사용자에게 확인한다.
- 세션 중에 저장소나 브랜치가 바뀌면 "작업 위치가 바뀌었다" 블록으로 새 위치의 태스크가 주입된다(worktree 진입·이탈은 즉시, 터미널에서 바꾼 브랜치는 다음 프롬프트에서). 그 뒤의 기록은 새 태스크에 한다. 직접 Bash로 브랜치를 바꿨다면 주입을 기다리지 말고 `where`로 현재 태스크를 확인한다.

## 상위 태스크와 연관 태스크

- **상위 태스크(`parent`)**: 여러 브랜치로 나뉘어 진행되는 큰 흐름(예: 여러 모듈의 독립화)을 묶는다. 상위 태스크는 보통 브랜치 없는 태스크(`--no-branch`)으로 만들고, 각 브랜치 태스크를 `--parent`로 그 아래에 둔다. 계층은 한 단계만 허용된다.
  - 하위 태스크 세션에는 상위 태스크의 state.md 전문과 결정 제목이 함께 주입된다. 이 세션의 할 일은 하위 태스크 state.md를 따른다. **상위 태스크의 유효한 결정을 따른다.** 어긋나는 결정이 필요하면 사용자에게 확인한다.
  - 흐름 전체에 걸친 결정은 상위 태스크의 decisions.md에, 이 브랜치에만 해당하는 결정은 하위 태스크의 decisions.md에 기록한다.
  - 상위 태스크의 state.md는 흐름 전체의 목표와 하위 태스크에서 나온 결과를 짧게 유지한다. 하위 태스크 목록은 `parent`로 `list`에서 알 수 있으므로 state.md에 나열하지 않는다. 하위 태스크에서 단계가 끝나거나 하위 태스크가 종료되면 상위 태스크의 "현재 상태"에 결과를 한 줄 반영한다.
- **연관 태스크(`related`)**: 후속 태스크, 같은 영역의 이전 태스크 등 의미를 정하지 않은 참조 목록이다. 주입되지 않고 ID만 표시되므로, 필요할 때 `list --all`로 위치를 찾아 읽는다.

## 여러 태스크를 병렬 에이전트로 진행할 때

- 태스크마다 별도 브랜치와 worktree에서 진행하는 것을 기본으로 한다. 서브에이전트는 `isolation: worktree`로 띄운다. 포커스는 프로젝트당 하나라 병렬 작업에 쓰지 않는다.
- 메인 에이전트는 서브에이전트에 넘기는 지시에 태스크 ID와 이 절의 규칙을 넣는다. 서브에이전트는 태스크를 새로 만들지 않고, 자기 브랜치를 `link <id>`로 그 태스크에 연결한 뒤 `where`로 확인한다.
- 서브에이전트는 세션 시작 주입을 받지 않으므로 태스크와 상위 태스크의 state.md·decisions.md를 직접 읽는다. 서브에이전트의 Bash `cd`는 다음 호출로 이어지지 않으니 기대지 않는다.
- 각 에이전트는 자기 태스크 기록만 고친다. 상위 태스크 반영(현재 상태 한 줄, 흐름 전체의 결정)은 메인 에이전트가 결과를 모아 한다. 동시에 고치면 서로 덮어쓴다.
- main 병합·푸시는 메인 에이전트가 결과를 모은 뒤 한 번에 한다.

## 파일별 작성 규칙

모든 파일은 UTF-8(BOM 없음), LF로 저장한다. 파일 편집은 Edit 도구로 직접 한다.

frontmatter(state.md, knowledge 항목)는 YAML의 일부만 읽는다. 맨 앞 열의 `key: 값`과 목록(`[a, "b, c"]`, 또는 빈 `key:` 아래 `  - 항목`)만 쓴다. `#`나 `: `가 들어간 값은 따옴표로 감싼다. 줄 끝 주석(`  # 설명`)은 쓸 수 있다. 중첩 구조, 여러 줄 값(`|`, `>`)은 오류가 되어 그 태스크가 목록에서 빠지므로 쓰지 않는다. 고친 직후 hook이 오류를 알려 주면 바로 고친다.

### state.md (현황, 덮어씀)
- 세션 시작 시 이것만 읽어도 이어서 작업할 수 있게 쓴다. **60줄 이내**를 유지하고, 넘으면 지난 내용을 log.md로 옮긴다.
- 섹션: 목표 / 현재 상태 / 다음 할 일 / 미해결 질문 / 핵심 파일(`경로:줄 — 역할`) / 관련 지식(`- K0012 제목`).
- frontmatter의 `design_doc`에는 Claude Docs 설계 문서 URL을 둔다(아래 "문서 위치 기준").
- frontmatter의 `parent`, `related`는 직접 고치지 말고 `relate` 명령으로 바꾼다(한 단계 제한과 ID 검증을 위해).
- 갱신할 때 frontmatter의 `updated`를 오늘 날짜로 바꾼다. 내용을 코드와 대조해 확인했다면 `verified`도 바꾼다.
- 커밋 해시는 적지 않는다(rebase로 바뀐다). 브랜치명과 커밋 메시지로 가리킨다.

### decisions.md (결정, 항목 추가)
- 사용자와 방향을 확정한 **즉시** 기록한다. 나중으로 미루지 않는다.
- 형식: `## Dn. 제목  (YYYY-MM-DD, 유효)` 아래에 결정 / 이유 / 기각한 대안 / 영향 범위.
- 결정이 바뀌면 기존 항목을 지우지 않는다. 상태를 `대체됨 → Dm`으로 바꾸고 새 항목을 추가한다.
- 기각한 대안과 그 이유를 꼭 남긴다. 같은 논의를 반복하지 않게 하는 핵심 정보다.

### log.md (히스토리, 덧붙이기만)
- `## YYYY-MM-DD HH:MM` 아래에 짧은 bullet로 적는다. 기존 항목은 수정하지 않는다.
- 무엇을 했는지보다 **무엇을 알아냈는지**(원인, 확인한 사실, 막힌 지점)를 중심으로 쓴다.

## 갱신 시점

- 결정을 확정했을 때: decisions.md에 즉시 기록. 그 결정이 태스크가 끝나도 유효한 코드베이스 설계라면 knowledge 기록도 제안한다(`agent-desk:kn`).
- 함정이나 원인을 밝혀냈을 때: log.md에 기록하고, knowledge 기록을 제안한다.
- 의미 있는 단계가 끝났을 때(원인 규명, 구현 완료, 방향 전환): state.md 갱신 + log.md 항목 추가.
- 사용자가 태스크를 마무리하거나 세션을 정리하려 할 때: state.md의 "다음 할 일"이 최신인지 확인.
- 컨텍스트 압축 직후(세션 컨텍스트에 압축 안내가 있을 때): 빠진 내용을 기록.
- 마일스톤(설계 확정, 구현 단계 완료)에서 설계 문서(`design_doc`)가 있으면 decisions.md를 바탕으로 갱신한다.
- 구현이 끝났을 때(PR 전): 아래 "저장소 문서" 기준으로 반영이 필요한지 점검해 제안한다.
- 갱신은 짧게 하고, 사용자에게는 "agent-desk 갱신" 정도로 한 줄만 알린다.

## 문서 위치 기준

| 내용 | 위치 | 쓰는 시점 |
|---|---|---|
| 태스크 단위 설계: 배경, 목표, 대안, 결정, 진행 | Claude Docs 설계 문서 (`state.md`의 `design_doc`) | 설계 단계부터 태스크와 함께 |
| 시스템의 현재 구조·기능·데이터 포맷·도메인 | 저장소 문서 (프로젝트 지침이 가리키는 위치, 예: `Docs/`) | 코드를 바꾼 같은 브랜치에서, PR 전 |
| 원자적 사실: 함정, 원인, 방법 | knowledge 항목 (`agent-desk:kn`) | 발견 즉시 |
| 사용자와 일하는 방식 | 에이전트 메모리 | 교정을 받았을 때 |

### Claude Docs 설계 문서
- 아래 중 하나 이상에 해당하면 만들기를 제안하고, 만들기 전에 사용자에게 한 줄로 확인한다.
  - 여러 세션에 걸칠 태스크
  - 대안을 비교해 고른 설계 결정이 있음
  - 여러 모듈이나 계층(코드, 데이터, 에셋, 서버/클라)에 걸친 변경
  - 리뷰하거나 공유할 예정
- 문서는 docs 스킬(예: `anthropic-skills:docs`)의 절차로 만들고, URL을 `state.md`의 `design_doc`에 기록한다.
- `decisions.md`가 원본이고 설계 문서는 사람이 읽는 정리본이다. 설계 문서의 각 결정에 `D3`처럼 원본 번호를 표시해 추적할 수 있게 한다.

### 저장소 문서
프로젝트 지침에 문서 기준이 있으면 그것을 우선한다. 없으면 아래를 따른다.
- **기존 문서가 다루는 시스템의 동작을 바꿨으면 규모와 관계없이 그 문서를 갱신한다.** 틀린 문서는 문서가 없는 것보다 해롭다.
- **새 문서**는 아래를 모두 만족할 때만 제안한다.
  1. 프로젝트 고유의 시스템, 데이터 포맷, 도구다. 엔진이나 라이브러리 일반 지식은 해당하지 않는다.
  2. 여러 파일과 계층에 걸쳐 있어서 코드 한 곳만 읽어서는 전체 그림이 잡히지 않는다.
  3. 태스크가 끝난 뒤에도 리뷰, 디버깅, 기능 추가 때 반복해서 볼 내용이다.
  4. 문서 색인(예: `Docs/README.md`)에 "언제 보나"를 한 줄로 쓸 수 있다. 이 한 줄이 써지지 않으면 문서로 만들 대상이 아니다.
- 기준에 못 미치면: 파일 하나의 동작은 코드 주석, 사실 하나는 knowledge, 태스크에 묶인 설계는 Claude Docs.
- 저장소 문서는 현재 코드 기준으로 쓴다. 설계 의도, 기각한 대안, 진행 경과는 넣지 않는다.
- 새 문서를 만들면 문서 색인에도 링크를 추가한다. 반영은 코드와 같은 브랜치에 커밋되어야 하므로 PR 전에 제안한다.

## 읽을 때의 태도

- 기록은 **확인할 출발점**이지 사실이 아니다. `verified` 날짜가 오래되었거나 코드와 어긋나면 코드를 우선하고 기록을 고친다.
- log.md는 필요할 때만 검색해서 읽는다. 통째로 읽지 않는다.
- 세션 컨텍스트에 동기화 충돌 사본 경고가 있으면 사용자에게 알리고 병합 여부를 확인한다.

## 종료와 재개

종료는 `agent-desk:desk-close` 절차를 따른다. 멈출 때는 `status <id> on_hold`, 다시 시작할 때는 `status <id> in_progress`를 쓴다.

- 하려다 그만둔 일은 `close <id> cancelled`로 기록을 남긴다. 잘못 만들었거나 중복인 태스크는 `delete <id>`로 휴지통에 옮긴다. 되살릴 때는 `restore <id>`.
- 영구 삭제(`delete <id> --purge`)는 사용자가 명시적으로 요청할 때만 한다. 출력의 `note`(동기화·백업의 버전 기록에는 남을 수 있음)를 사용자에게 전한다.
- 휴지통의 태스크는 목록·주입·브랜치 매칭에서 빠진다. 그 태스크를 가리키던 상위·연관 태스크와 포커스는 그대로 두며, 되살리면 다시 이어진다.
